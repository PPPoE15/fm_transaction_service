# Сервис управления транзакциями

## CI → публикация Docker (FM-65)

`.github/workflows/lint-and-test.yml` запускает Ruff, проверку форматирования,
Mypy и полный Pytest (включая Postgres через testcontainers) на `pull_request`
и push в `dev`/`master`. Job `publish` зависит от успешного `lint-and-test`:
failed/cancelled/skipped проверки не разрешают публикацию. Успех другого запуска
или другого SHA не используется. Checkout обеих jobs закреплён на `github.sha`;
на PR это проверяемый merge commit, публикация на PR всегда пропускается.
Секреты Docker Hub доступны только шагу входа в job публикации.

На push Docker target равен имени ветки (`dev` либо `master`), платформа —
`linux/amd64`. Требуются secrets `DOCKERHUB_USERNAME` и `DOCKERHUB_TOKEN`.
Версия образа: `<username>/fm_transaction_service:<target>-<полный SHA>`.
Разные target имеют разные версии даже при одинаковом SHA. Публикации одного
окружения сериализованы через concurrency без отмены выполняющейся job.
Повторный запуск сначала ищет версию в реестре и использует существующий digest
без пересборки и перезаписи. Только явное отсутствие manifest разрешает сборку;
ошибки сети/авторизации останавливают job. После частичной публикации повторный
запуск также восстанавливает метаданные из существующего образа.

Для деплоя используйте поле `image` (`repository@sha256:…`) из `publication.json`.
Этот файл сохраняется как artifact
`publication-<target>-<SHA>-<run_attempt>` и выводится в summary; содержит также
`tag`, `sha`, `environment`. Job outputs: `digest`, `sha`, `environment`. Полная ссылка передаётся через artifact:
GitHub может скрывать job outputs, содержащие имя пользователя из secrets.
Старый самостоятельный workflow удалён. После публикации или повторного использования
SHA-версии тег `dev`/`master` обновляется на её digest без пересборки. Поэтому
`make up_dev` и `make update_transaction` в `fm_devops` получают опубликованный
образ через тег `:dev`. Ошибка обновления тега останавливает публикацию до записи
успешных метаданных. В логе выводятся обновлённый тег и digest.
Для развёртывания конкретного запуска используйте точную ссылку из `publication.json`.

Гарантия отсутствия перезаписи относится к этому workflow: сторонним издателям
не следует выдавать права на запись тех же версий. При настройке Docker Hub
можно дополнительно включить неизменяемость тегов `<target>-<SHA>`.

### Проверка

`poetry run pytest src/tests/test_publication.py` проверяет связь jobs, сохранение
обязательных проверок, отсутствие секретов в CI, удаление старого пути публикации,
первую/повторную публикацию обоих target, отказ при failed/cancelled/skipped CI,
PR и ошибке реестра с подменённым
Docker CLI. Это проверки конфигурации и скрипта, а не публикация в Docker Hub.
Реальный PR должен показывать успешный CI и skipped `publish`.
После merge первый push в `dev`/`master` проверяется в Actions: сначала CI, затем
публикация, artifact и совпадение SHA/target/digest. На тестовой ветке workflow
можно проверить ошибку обязательной проверки и отмену CI: `publish` не запускается.
Не ломайте рабочую `dev`/`master` ради такой проверки.

## SSH deployment (FM-66)

После успешной публикации workflow передаёт digest серверному контроллеру fm_devops
через SSH. Push в dev/master использует соответствующий GitHub Environment.
Master требует required reviewer в настройках окружения.
Подготовка SSH, environment secrets и процедура восстановления:
[fm_devops deployment guide](https://github.com/PPPoE15/fm_devops/blob/dev/docs/deployment.md).
На сервере должен быть установлен контроллер FM-66 и выполнен bootstrap.
Повторять неудачный деплой через Re-run failed jobs, сохраняя digest успешной публикации.
Клиент `scripts/deploy-ssh.py` выводит проверку входных данных, SSH-этап, digest и время
операции. При отказе он показывает безопасное описание ошибки подключения или
ответа контроллера. Если контроллер указал журнал, прочитайте его на сервере
в `DEPLOY_ROOT/logs`. Итог и применённые digest доступны в Job Summary.

Проверка клиента: `python3 -m unittest discover -s scripts/tests -p test_deploy_ssh.py -v`.

## Воркер продления регулярных операций (FM-116)

В локальном Compose `make up_all` запускает API и сервис
`regular-operations-worker`. Воркер использует образ API, стартует после
`_init-migrations` и сразу обрабатывает пропущенные даты. Затем продлевает
горизонт ежедневно в 03:00 по Москве. Для другого времени укажите, например,
`REGULAR_OPERATIONS_RUN_AT=04:30 make up_all`.

В опубликованном образе команда из каталога `src` —
`python -m apps.workers.regular_operations`. Контейнеру нужны те же настройки
PostgreSQL (`DB_*`), что и API. Миграции применяются до запуска контейнера.
Воркеру не нужны HTTP-порт и ключи JWT.

Журнал локального процесса доступен через
`docker compose -f docker/docker-compose.yml -p financial_manager logs regular-operations-worker`.
Итог прохода содержит дату, количество обработанных регулярных операций,
созданных планов и ошибок. Ошибка отдельной операции сохраняется как её UID и
тип ошибки. Проход продолжится, а необработанный диапазон останется доступен
при следующем запуске. При ошибке чтения очередной страницы процесс завершается
с ненулевым кодом, и Compose перезапускает его. После `SIGTERM` воркер завершает
текущую команду в пределах времени остановки контейнера.
